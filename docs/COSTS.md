## Operational reality

D1 indexes and FTS triggers amplify writes. A five-product batch can write multiple rows per product; source-run counts are not billing rows. Popular-query caching is not enabled because search URLs may contain private ideas. Short public product/category cache headers help browser/CDN reuse but do not remove every Worker invocation. Track actual D1 `rows_read`, `rows_written`, storage, Worker CPU and requests in the dashboard. The ingestion cap defaults to 100 candidates/run in daily Actions (hard code maximum 100). Turn it off with `DISCOVERY_ENABLED=false` if quotas approach limits.

A public repository reveals source code, not submission PII. Do not use private runners/jobs as a workaround without reviewing billing. GitHub schedules can be delayed or dropped and automatically disable after 60 days of repository inactivity; reenable manually. This operational limit prevents a guarantee of permanent unattended discovery without maintenance.

Structured application logs omit query strings and submission contents. Invocation URL logs are disabled; query strings are explicitly redacted in observability. Trace sampling is 1%. Keep account observability on its Free offering and inspect retention/quotas before launch.

Deployment confirmed that custom `limits.cpu_ms` is rejected on Free (100328). The override is omitted and Cloudflare’s Free 10ms limit applies. No plan change was made.

## Measured production usage

The account dashboard showed **Free / $0 / Current plan** before provisioning. No upgrade, payment method, paid model, paid runner, or paid integration was added. Resources are isolated to this application.

After text-processing improvements, a bounded cache of public catalog text, and Worker minification, the final separate 60-search window reported 60 observed requests, zero errors/subrequests, CPU p50 **1.942ms**, and p99 **5.993ms**. Network p50/p95 were 172.32/234.08ms. The sampled search p99 is below the Free 10ms allowance. Earlier retained mixed/cold windows measured 12.434–25.607ms p99. This is an improvement in a bounded sample, not a sustained all-route or cold-request guarantee; provider enforcement can terminate requests. Keep checking real traffic and simplify normalization/ranking or reduce candidate hydration if CPU errors appear. No automatic upgrade is configured.

One representative production search read **46 D1 rows**, wrote **zero**, and used **1.5934ms** SQL execution time across retrieval and hydration. This is a measurement for that query, not a worst-case quota estimate. At the same read cost, 100,000 searches would consume 4.6 million reads, close to the account-wide five-million daily allowance before other traffic. Storage at measurement was 266,240 bytes. Ingestion and FTS triggers add writes separately.

## Expanded catalog

The 2,785-product backfills completed on the same Free infrastructure. Discovery checks up to 100 candidates every six hours; Homebrew checks up to 500 every six hours and Awesome-Selfhosted up to 500 daily (manual ceiling 2,000). Already-seen URLs are skipped. Bulk imports amplify FTS writes; watch account-wide quotas before further large runs. The first 60-query expanded-catalog window had zero errors, CPU p50 4.317ms and p99 16.199ms. This exceeds the 10ms Free allowance at the tail and is retained in `catalog-scale-cpu.json`; availability in one sample does not guarantee future provider enforcement. The public-text cache is bounded to 1,024 records and never stores user queries. See the expansion report for subsequent checks.

The final separate window after the bounded cache/collation update measured CPU p50 4.134ms and p99 11.840ms over 59 provider-observed requests (zero errors/subrequests); all 60 client queries returned HTTP 200. The sampled tail remains above 10ms. Network p50/p95 were 217.75/411.02ms. Raw results are in `catalog-scale-search-final.json` and `catalog-scale-cpu-final.json`.
